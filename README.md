# Agents-Research

四个开源 Agent 项目的**代码级横向对比研究**。按 Agent 运行时的架构层次逐层深入，每层产出一篇对比分析，每篇沿同一条**七问链**推进——先界定范围，再逐维对比，最后落到可执行的设计结论（见第四节）。

全文按**三区**组织：**启动区**（循环之前，`L0.1` / `L0.2`）、**内核区**（一轮循环及其子系统，`L1`–`L10`）、**外围区**（内核之外，`L11`–`L15`）。**章编号表示撰写批次，层次槽位表示架构位置，两者是两套坐标**——内核区已有先例（第 10 章先于第 9 章写成）。当前进度：内核 01–10 与启动区第 12 章已完成，其余槽位已在第二节登记。

所有断言均标注 `文件:行号`，可回到源码逐条核验。

## 四、每篇回答的同一组问题

各篇沿同一条**问题链**推进，**一问对应一节**。顺序是先界定范围、再逐维对比、最后落到设计结论：

| # | 问题 | 对应节 | 产出物 |
|---|---|---|---|
| **Q1** | 这一层是什么？管什么、不管什么？上下游是谁？ | 二、本层职责与边界 | 子职责拆解 + 层次定位图 |
| **Q2** | 同一个概念，四家分别叫什么？ | 三、概念对齐表 | 横向对齐表（空白格 = 该项目无对应物） |
| **Q3** | 四家各自的核心流程是什么？入口 → 主流程 → 状态载体怎么走？ | 四、逐项目实现 | 源码摘录，每个断言附 `文件:行号` |
| **Q4** | 同一维度上四家分别怎么做？共识度多高？ | 五、横向对比矩阵 | 一维度一矩阵，附「共识度」列 |
| **Q5** | 出错、越界、被中断时四家怎么办？为什么这么办？ | 六、异常与降级 | 场景 → 四家做法 → 源码依据 → **设计理由** |
| **Q6** | 哪些能直接采纳？哪些要按产品形态权衡？哪些明确不该做？ | 七、设计建议 | 共识 / 推荐 / 权衡 / 反例 四级 |
| **Q7** | 这些结论在源码哪里？怎么复核？ | 附录：关键文件索引 | 项目 / 文件 / 行号 / 用途 四张表 |

「一、核心结论速览」是把 Q1–Q6 的答案压成一屏摘要（≤5 条），不是独立一问。规范细节见 `00-总览与导航.md` 第七节。

**两个易混点**

- **「边界」有两个意思**：Q1 的「边界」是**职责范围**（这层管什么、不管什么），Q5 的「边界」是**异常情形**（出错、越界、被打断时的行为）。第六节标题已正名为「异常与降级」，与第二节的职责界定彻底分开，不再共用一词。
- **「共识度」是 Q4 通往 Q6 的桥梁**：四家一致 → 进 Q6 的「共识」级；只有一家这么做 → 进「权衡」级。因此 Q6 的每条建议都能回溯到 Q4 的某个矩阵行，而不是拍脑袋的主观意见。

### 排版约定

| 元素 | 写法 |
|---|---|
| 章标题 | `# 第 N 章：主题 —— 一句副标题` |
| 导语段 | 章标题之后、元信息块之前的一段纯文字 |
| 一级分节 | **中文数字 + 顿号**（`## 五、横向对比矩阵`） |
| 二级 / 三级分节 | 阿拉伯数字，序号跟随上一级（`### 5.4`、`#### 4.4.3`） |
| 附录 | 不参与编号（`## 附录：关键文件索引`） |
| 图示 | 结构/层次用**盒线字符图**，流程/时序用 **Mermaid**；每篇至少 1 张盒线图 |
| 图注 | 紧跟图块之后，格式 `**图 N-M**：……` |
| 引用写法 | 跨章 `见第 N 章`；章内小节 `见 N.M`；文档自称「本篇」 |

> 不使用 `§` 节号：中英混排会同时损失可读性与检索一致性。

## 五、维护约定

### 命名与保留规则

- 文件名格式：`NN-主题.md`，`NN` 为两位序号。**章编号表示撰写批次，层次槽位（`L0.1` / `L1`–`L15`）表示架构位置**——新增一层必须先在 `00` 第二节模块地图里登记槽位，再取下一个可用章号；两者不要求同步（内核区已有先例：第 10 章先于第 9 章写成）。
- **每个模块只保留一份有效文档**：新版本直接替换同名旧文件，不保留历史版本。演进痕迹由 git 承载，不由目录冗余承载。

### 新增一篇的标准流程

1. **登记与可行性确认** —— 先在 `00` 的模块地图里登记四个项目的源码入口；若某个项目在该层确实没有实现（例如某项目没有独立的任务子系统），这是有价值的结论而非阻碍，需在「四、逐项目实现」中明确写成「未找到 / 用 X 机制替代」。
2. **并行复核锚点** —— 派 Explore 子代理对四个项目**并行**探索，要求每条结论附 `文件:行号` 与代码原文摘录。**不依赖记忆中的行号**，一律以 `grep -n` 实测为准。
3. **按七问链撰写** —— 严格按第四节逐问作答（一问对应一节），「三、概念对齐表」与「五、横向对比矩阵」必须是矩阵形式，不得写成按项目分段叙述。
4. **同步更新三处** —— ① `00` 的模块地图（含**层次槽位**与状态）与报告索引（含行数）；② 本 README 的文档地图与状态；③ 交叉核对已有篇章中涉及本层的断言，保持全系列口径一致，并检查索引层是否需要联动调整。**新层的槽位必须在写正文之前先登记**——槽位是架构坐标，章号只是撰写批次，两者不同步是允许的（先例：第 10 章先于第 9 章、第 12 章先于第 11 章写成）。

### 质量红线

- **每个结论都要能追到 `文件:行号`** —— 无法给出锚点的判断标注为 `[推断]`。
- **概念对比一律横向对齐** —— 同一个维度上四个项目并排，不写成四段项目介绍。
- **异常与降级（Q5）必须写「为什么」** —— 只写「做了什么」不算完成，要给出源码注释或设计上的理由。
- **反例必写** —— 「七、设计建议」的「明确不该做什么」比「推荐做什么」更难写，也更有价值。
- **区分设计动机与实现细节** —— 上游分歧（如消息模型差异）会向下传播到多层，写某层时要指出它继承自哪一层。
